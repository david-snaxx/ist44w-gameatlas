# GameAtlas: AI Assistant Context

**Read [`docs/PLAN.md`](docs/PLAN.md) before doing anything non-trivial.** It is the source of truth for
goals, data model, API contract, phases, and past decisions. This file is only a quick summary.

## What this project is
A web app for **Unity** game dev teams. Non-technical members (writers, designers, artists) create
**engine-ready game data** through schema-driven **forms** (flat and nested data) and a **node-graph editor**
(branching dialogue). Documents can **reference each other** across both editors. GameAtlas then generates the
**C# classes, ScriptableObject assets and dialogue runtime** to use that data in Unity. Solo IST 440W capstone by
David Reichart. Hard deadline **2026-12-01**.

**Unity is the target as of 2026-09-17** (PLAN.md §1). This changed the pitch and the outputs, **not the data
model**: stored and exported JSON never mentions Unity, and Unity support is an output layer on top of it
(PLAN.md §5.7). Don't put C#, ScriptableObject or TextMeshPro concerns into `frontend/src/schema/` or `frontend/src/data/`.

## Current stack (intent, can change; see PLAN.md §3)
- Frontend: React 19 + Vite 8, JavaScript. React Flow (`@xyflow/react` v12) powers the dialogue tree editor.
- Backend (Phase 2+): Node 24 + Express 5 in TypeScript (Node runs the `.ts` files directly, no build step), MySQL 8.4 through `mysql2` (JSON columns).
- Unity (Phase 5+): Unity 6 LTS, C#, TextMeshPro. A UPM package under `unity/`, plus a client-side C# generator in `frontend/src/unity/`.
- The repo has one folder per codebase (PLAN.md §4). `frontend/` holds the Vite app: the design system, shared components and the pages. `backend/` is the Express API (a health check, users with sign-up and login, and projects with their blueprints, assets and dialogues). `unity/` (the Unity package) doesn't exist yet. Docs (`docs/`, this file) and `.claude/` stay at the repo root.

## Rules to follow when working here
- **Never hand-code forms per schema.** All forms come from a schema definition through the generic `FormRenderer` (`frontend/src/components/form/`) and the field-type registry (`frontend/src/schema/fieldTypes.js`, PLAN.md §5.2–5.3).
- **The node editor is for dialogue trees only** (user decision, 2026-09-14). Dialogues have their own model (`frontend/src/data/dialogueGraph.js`), store and pages, and use dialogue wording (Line, Player choice, Check flag, Action, End). Speakers and items link to assets. The Phase 2 API can still store them as documents of a built-in graph schema.
- **Exported JSON is a contract for engine developers.** Keep it clean: no editor-only data such as node positions. Don't change its shape without updating `docs/export-format.md` and the decision log. It is also **engine-neutral** — the Unity-shaped decisions live in the output layer, not in the export.
- **Vector fields export as `{x,y,z}`** because that is what Unity's `JsonUtility` produces for `Vector2`/`Vector3`. Don't "simplify" it to an array.
- **Dialogue text may contain inline rich-text tags** (PLAN.md §5.8): TMP-native `<b>`, `<i>`, `<color=…>` pass through; GameAtlas effect tags `<wave>`, `<shake>`, `<speed=…>`, `<pause=…>` are parsed by the Unity runtime. They stay inline in the string. Keep the effect set small and fixed.
- **The backend is the authority on validation.** The frontend validates too, for UX. Both run the **same code**: the backend imports `frontend/src/schema/validation.js`, `fieldTypes.js`, `blueprintDraft.js` (`toDraft`/`toDefinition`, which clean every blueprint the API saves or sends), `frontend/src/data/assetData.js`, the dialogue checks in `frontend/src/data/dialogueGraph.js` and `checkContents()` in `frontend/src/data/backupFile.js` directly, so never port them to the backend. Keep those logic modules plain JavaScript with no React, browser APIs (`window`, `localStorage`, `document`) or Vite-only imports, or the backend can't load them.
- **Design for users with zero programming knowledge — and zero Unity knowledge.** Use dropdowns over free-text IDs, inline errors, and no raw JSON by default. Primary users should never have to open the Unity editor; that is the programmer's half of the workflow.
- The user is still learning React, JavaScript and TypeScript (strong in Java, Spring, and SQL). Keep React code idiomatic but simple, and briefly explain non-obvious React patterns. The backend uses TypeScript lightly: parameter types and a few interfaces, nothing clever.
- **Simple code over polish** (user decisions, 2026-09-23 and 24; PLAN.md §2.7). The code must stay easy for the user to read, so:
  - **No accessibility layer:** no `aria-*` attributes, `role`s, screen-reader-only text, focus management, custom focus rings or keyboard handlers. Native elements (`<button>`, `<select>`, checkbox, `<dialog>`) give basic keyboard use for free; that is enough (STYLE-GUIDELINES §12).
  - **No motion:** no transitions, animations or `prefers-reduced-motion` rules (§8).
  - **Prefer the browser's own controls** over custom widgets: `Select` is a `<select>`, `Checkbox` is a checkbox, `ConfirmDialog` is a `<dialog>`.
  - **Don't add props or CSS for small visual tweaks.** Add a prop only when a caller really needs different behaviour. Icon-only buttons get a `title` (tooltip) and nothing else.
  - **Readable over compact** (user request, 2026-09-24; the whole frontend and the backend follow it). The user reads Java/C# comfortably but not dense JavaScript, and the code should be easy for a very junior developer. More lines are fine. Concretely:
    - **No ternaries (`? :`).** Work out anything conditional before the `return` with `if`/`else` and a named variable, or return early. A function that returns different things per case is a chain of `if`s.
    - **`{condition && <Thing />}` only for one plain condition** (a boolean or a value that's set or not). Anything more gets a named variable first (`const showImportNotice = Boolean(imported) && !baseline`).
    - **Loops instead of chained array methods.** Use `for…of` (or a counting `for`) to build arrays, objects and totals — no `reduce`, `Object.fromEntries`, `flatMap`, or `.filter().map()` chains. A single `.find`/`.filter`/`.some`/`.map` with a one-line callback is fine (like C#'s LINQ).
    - **Lists in JSX:** a `.map()` is a one-liner that renders one element or a named component (`{items.map((item) => <LinkListItem key={item.to} item={item} />)}`), or the list is built with a loop before the `return`. Never a `.map()` inside another `.map()`.
    - **Split big components.** Each repeated or self-contained piece of markup is its own small component in the same file with a one-line doc comment (see `StatusBadge`, `SettingRow`, `PropertyPanel`). Data-building logic goes in plain helper functions below the components.
    - **Event handlers:** a one-line arrow that calls one function is fine (`onClick={() => setOpen(true)}`); anything longer is a named `function handleX()` before the `return`.
    - **Class names** are built with strings and `if` (`let className = 'nav-item'; if (isActive) className = 'nav-item is-active'`). There is no `cx` helper.
    - **Explicit object keys** (`{ label: label }`) over shorthand, and no destructuring beyond component props and hook results.
    - Use the `setX((current) => …)` form only when an update can run later or several times before a re-render (the Undo toast, React Flow's change handlers), and say why in a comment; otherwise pass the new value directly.
    - **Comments explain the thing they sit on, briefly** (user request, 2026-10-17; frontend and backend). Each function, component, exported constant, interface and non-obvious field gets one short doc comment (`/** … */`, one or two lines) saying what it is, takes or returns. Inside a function, add a one-line comment only for a *why* the code can't show: a gotcha (MySQL reordering JSON keys), a workaround, or a non-obvious React pattern. Don't narrate what the next lines do, retell history or decisions ("used to", "before this fix"), or repeat CLAUDE.md and PLAN.md; file headers are at most three lines.
- Favor MVP scope. Treat anything in PLAN.md's "Stretch / future" list as out of scope unless asked.
- **UI/styling work must follow [`docs/STYLE-GUIDELINES.md`](docs/STYLE-GUIDELINES.md)**, which is the authoritative design system. [`docs/STYLE-GUIDE.md`](docs/STYLE-GUIDE.md) is the filled-in questionnaire it was derived from (for background only). Keep all colors, fonts and spacing in shared CSS variables rather than hard-coding values in components.
- **Shared components have no CSS Modules.** Everything in `frontend/src/components/` is styled by global classes in `frontend/src/styles/base.css`, **one block per component** that holds every rule for its classes (`display`, `gap`, colors, …), even if that repeats a line from another block (user decision, 2026-09-24). Don't add a `.module.css` there, and don't group selectors from different components together. Small helpers used directly in markup (`.row`, `.between`, `.push-right`, `.stack`, `.muted`, `.subtle`, `.small`, `.truncate`, `.field-error`) live in the Utilities block. Pages keep their own `.module.css` for layout; it loads after `base.css` and so overrides it (STYLE-GUIDELINES §13).
- **User-facing wording:** Schema → "Blueprint", Document → "Asset", Field → "Property", Key → "ID". Frontend modules and components use the UI names (`blueprintStore`, `AssetEditorPage`), but saved/exported data keys (`schemaId`, `schemaVersion`, `fields`, `key`) and future API/database names stay `schema`/`document`/`field`/`key`.
- When a design decision changes, update the relevant PLAN.md section **and** add a line to the decision log (§11).

## Frontend structure so far
- `frontend/src/styles/tokens.css` (all design tokens) and `frontend/src/styles/base.css` (reset, background glows, utilities, then one block per shared component)
- `frontend/src/components/`: reusable components. Every page renders inside `AppShell` (frame with top bar, sidebar and status bar, around a scrolling content zone). The full inventory with props is in STYLE-GUIDELINES.md §7.10; **reuse or extend these before creating new components.**
- **Pages compose shared page-level components, not their own chrome.** A list page returns `<ListPage>` (heading, search toolbar, table, empty states); a missing blueprint/asset/dialogue returns `<MissingRecord>`, and one still on its way from the server (or that couldn't be loaded) returns `<LoadingRecord error={…}>`; the top bar's Import/New pair is `<TopBarActions>`; editors guard leaving with `useUnsavedChanges(isDirty)` from `frontend/src/utils/` plus `<UnsavedChangesDialog>`; "opened pre-filled" and out-of-date messages are `<Notice>` / `<ImportNotice>`; downloading a whole collection goes through `downloadCollection()` in `frontend/src/utils/downloadJson.js`, which refuses while anything has problems. Don't rebuild these per page.
- **Page layout comes from global classes too.** `.page`, `.page-head`, `.page-intro`, `.page-actions`, `.toolbar`, `.panes`, `.subhead` and `.settings-heading` live in `base.css`'s Page layout block. A side-by-side editor is `<div className="panes" style={{ '--panes': '260px minmax(0, 1fr) 340px' }}>` — the rule in the gutter comes with it. Only add a page `.module.css` when the layout is genuinely unique to that page (the dashboard, settings, the asset view, the graph canvas and nodes, the blueprint property tree).
- **Pages are flat (STYLE-GUIDELINES §6.1).** Every piece of a page is a `Section`: no background, no border box, no radius. Stacked sections are separated by the rule under each title and `--space-6`; side-by-side panes by a vertical rule with `--space-5` either side (the `.panes` class). The only cards left are the dashboard's three entry tiles and the graph canvas's hairline. **Don't add new cards** — use a rule and more space.
- Overlays opened from inside a `Section` (the side panel, the dialogue editor's "Add next step" menu) must use `createPortal` to `document.body`: section bodies scroll and would clip them, and `backdrop-filter` (still on the dashboard cards and every floating layer) traps `position: fixed`. Dropdowns are native `<select>`s, so they need nothing.
- **Forms:** put the input inside `PropertyRow` as a child (`<PropertyRow label="Name" error={error}><TextInput … /></PropertyRow>`). Labels move above inputs by themselves in narrow places. Inputs built by `FormRenderer` get the id `field-<path>`, which is what `ValidationSummary` focuses; give a hand-built input an `id` only when a validation summary needs to jump to it.
- When changing glass, glow or text color tokens, check that text is still easy to read on them (STYLE-GUIDELINES.md §5.6).
- **Opening an editor pre-filled** (import or Duplicate) means navigating to its `/new` route with state `{ imported, origin: 'file' | 'duplicate', originName }`. Use `duplicateAssetState`, `duplicateBlueprintState` and `duplicateDialogueState`. Nothing is saved until the user clicks Save (STYLE-GUIDELINES.md §7.15).
- `frontend/src/api/`: fetch wrappers for the REST API, one file per resource, all built on `sendRequest(method, path, body?)` in `request.js`. Addresses are relative (`/api/...`) because Vite passes those to the backend, so the browser sees one address: no CORS, and the session cookie is sent back on its own. Every call answers `{ data }` (the server's JSON, or `null` for a 204) or `{ error }` with a message to show — the server's own wording, not invented here. Field-level problems also come back as `errors` (the server's `[{ path, message }]`), with `error` set to the first message, so `if (result.error)` always catches a failure. `users.js` has `signUp()`, `logIn()`, `logOut()` and `getMe()`; `projects.js` has `listProjects()` (oldest first), `createProject(name)` and `replaceProjectContents(projectId, contents)`; `blueprints.js` has `listBlueprints(projectId)`, `createBlueprint(projectId, blueprint)`, `updateBlueprint(projectId, blueprintId, blueprint)` (`blueprintId` is the saved ID; a different `blueprint.id` renames it) and `deleteBlueprint(projectId, blueprintId)`; only `blueprintStore.js` (and the project store, for the sidebar's other projects) calls them. `dialogues.js` has `listDialogues(projectId)`, `createDialogue(projectId, dialogue)`, `updateDialogue(projectId, dialogueId, dialogue)` and `deleteDialogue(projectId, dialogueId)`; only `dialogueStore.js` calls them. `assets.js` has `listAssets(projectId)`, `createAsset(projectId, asset)`, `updateAsset(projectId, assetId, asset)` and `deleteAsset(projectId, assetId)`; only `assetStore.js` calls them. `currentUserStore.js` + `useCurrentUser()` hold who is logged in: they ask `GET /api/users/me` **once per page load** and share the answer, so the sidebar and the account page agree without each asking. The login page calls `setCurrentUser()` so the name shows without a second request, and the sidebar's Log out calls `clearCurrentUser()`. `currentProjectStore.js` + `useCurrentProject()` do the same for the logged-in user's projects (`{ checked, project, projects, blueprints, error }`): once per page load, and again when a different user (or nobody) is logged in. A user with **no projects** (their first login) gets a personal one, `"<display name> (personal)"`, filled with the starter examples (`STARTER_BLUEPRINTS`, `STARTER_ASSETS`, `STARTER_DIALOGUES`) through `replaceProjectContents()`. Until there's a project picker, `project` (the one they work in) is the oldest, which is that personal project. **Blueprints, assets and dialogues are all saved on the server (2026-10-16)**; nothing reads localStorage for them any more. Every page about one of them needs a login: it shows `LoadingRecord`'s "Log in to see your …" otherwise, and the list pages are empty.
- `frontend/src/schema/`: the blueprint (schema) layer. `fieldTypes.js` (type registry), `validation.js` (form values and blueprint definitions), `blueprintDraft.js` (editor drafts with `uid`s ↔ clean saved definitions, tree helpers), `blueprintStore.js` + `useBlueprints.js`: the current project's blueprints, **saved on the server** and kept in memory like the assets (see `data/assetStore.js`); pages must go through it. `loadBlueprints(projectId)` fetches the list once per page load. `saveBlueprint(definition, previousId)` (`previousId` null for a new one) and `deleteBlueprint(id)` call the API, wait for the server, put its answer into the list and answer `{ data }` or `{ error }`; the server decides the version (1 for a new blueprint, one more when a saved one changed, unchanged otherwise) and trims the name, and a rename reloads the list, because the server moves other blueprints' links in the same request. `replaceBlueprints(projectId, blueprints)` takes the server's answer after a whole-project replace. `useBlueprints()` is the plain list; `useBlueprint(id)` answers `{ status: 'loading' | 'found' | 'missing' | 'failed', blueprint, error }`, and `useBlueprintsStatus()` just `{ status, error }`. **A page that reads a blueprint from the URL waits for it** (`LoadingRecord`): the builder, and the asset list, view and editor, whose form is built from the blueprint's properties when it opens.
- `frontend/src/data/`: the asset (document) layer. `assetStore.js` + `useAssets.js`: the current project's assets, **saved on the server** and kept in memory (not localStorage) as the list every page reads; pages must go through it. `loadAssets(projectId)` fetches the list once per page load (and again for another project). `saveAsset({ id?, key, schemaId, data })` (no `id` means new) and `deleteAsset(id)` call the API, **wait for the server**, put its answer into the list and answer `{ data }` or `{ error }`; a rename reloads the list, because the server moves the links in other assets in the same request. `replaceAssets(projectId, assets)` takes the server's answer after a whole-project replace. `useAssets()` is the plain list (empty while loading), so list pages need nothing else; `useAsset(schemaId, key)` answers `{ status: 'loading' | 'found' | 'missing' | 'failed', asset, error }` for pages about one asset. `deleteAssetsOfBlueprint()` and `moveAssetsToBlueprint()` bring the copy in memory in line after the server deleted or renamed a blueprint (the server deletes its assets, and assets follow a rename by themselves); the builder calls them after a successful save or delete. `assetData.js` (saved data ↔ form values, display names, link renaming, the export shape `{ id, blueprint, blueprintVersion, data }`, file import). Dialogues: `dialogueGraph.js` (node types, validation, export shape, `dialogueLinksToAsset` and `renameAssetInDialogue`), `parseDialogueFile` (import with auto-layout), and `dialogueStore.js` + `useDialogues.js`: the current project's dialogues, **saved on the server** and kept in memory like the assets. `saveDialogue({ id?, key, name, description, speakerBlueprint, itemBlueprint, nodes, edges })` and `deleteDialogue(id)` wait for the server and put its answer into the list; only the name and ID are checked, so an unfinished tree saves. `replaceDialogues(projectId, dialogues)` takes a whole-project replace's answer. `retargetDialogueBlueprint()` (after a blueprint rename) and `moveAssetLinks()` (after an asset rename) bring the copy in memory in line with what the server already changed. `useDialogues()` is the plain list; `useDialogue(key)` answers `{ status, dialogue, error }`. The editor compares JSON snapshots to spot unsaved changes, and MySQL returns the keys inside each node in a different order, so **a snapshot is only ever compared with one taken from the same source** (Discard takes a new one from the saved copy it restores). `backupFile.js`: the backup file format (`createBackup`, `parseBackupFile`, `describeContents`) and `checkContents()`, which checks a whole `{ blueprints, assets, dialogues }` set against itself before `PUT /api/projects/:id/contents` replaces a project with it; plain logic, so the backend imports it. `backup.js`: restore, reset to examples and delete all. `restoreData()` sends the whole set to `PUT /api/projects/:id/contents`, waits, and then puts the server's answer into every store (each has a `replace…` function), so the server and the still-local blueprints and dialogues match; it answers `{ data }` or `{ error }`. It passes `backupFile.js`'s functions on so the Settings page imports from one place.
- Routes live in `frontend/src/App.jsx` (`react-router` v8 data router): `/` (home dashboard), `/blueprints` (list), `/blueprints/new` and `/blueprints/:blueprintId` (builder), `/assets` (all assets across blueprints), `/blueprints/:blueprintId/assets` (one blueprint's asset browser), `/blueprints/:blueprintId/assets/:assetKey` (read-only asset view with export), `/blueprints/:blueprintId/assets/new` and `/blueprints/:blueprintId/assets/:assetKey/edit` (asset editor), `/dialogues` (list), `/dialogues/new` and `/dialogues/:dialogueKey` (tree editor), `/settings` (backup, restore, reset), `/login` and `/signup` (the only pages outside `AppShell`; STYLE-GUIDELINES §7.16), `/account` (the logged-in user; §7.17), `*` (not found).

- `npm run build`: production build
- `npm run lint`: ESLint

## Commands (backend, run inside `backend/`)
- `npm run dev`: start the API on port 3000 and restart it when a file changes. It watches only `backend/src` and the three frontend folders the backend imports from (`frontend/src/schema`, `data` and `utils`), each with `--watch-path`; a backend import from any other frontend folder needs adding there too. Plain `--watch` and `--env-file` both make Node watch `node_modules`, where Windows reports even reading a file as a change (this machine keeps "last accessed" times), so the server restarted by itself. `.claude/launch.json` has the same thing as the `backend` config, with paths from the repo root.
- `npm start`: start without watching. `npm run typecheck`: check types with `tsc` (TypeScript 7). Node runs the `.ts` files itself, so `tsc` never builds anything.
- Settings come from `backend/.env` (gitignored; copy `.env.example`), which `src/config.ts` loads with `process.loadEnvFile()` when it exists (not with the `--env-file` flag; see `npm run dev` above). A variable already set in the environment wins over the file. The server doesn't restart when `.env` changes, so restart it by hand after editing it. `SESSION_SECRET` signs the login cookie; it has a local-only fallback, and a deployed server must set its own. `src/config.ts` reads them all and has local defaults. MySQL 8.4 runs as the Windows service `MySQL84`; the app uses a `gameatlas` database and user.
- `GET /api/health` answers `{ server, database }`; `database` is `"unreachable"` (status 503) until the `.env` login works, and the reason is logged in the server's console.

## Backend structure so far
- `backend/src/server.ts` starts the app; `app.ts` builds it (JSON body parsing, routers under `/api`, then a JSON 404 for unknown `/api` addresses and a JSON error handler). Bodies are limited to `express.json()`'s 100 KB, except `PUT /api/projects/:id/contents`, which gets its own parser with `PROJECT_CONTENTS_LIMIT` (20 MB) registered before the general one. The error handler answers a body that's too big with 413 and one that isn't JSON with 400; anything else is logged and answers 500. Keep them apart so tests can use `app` without opening a port.
- `backend/src/routes/`: one Express router per resource (like a Spring controller), mounted in `app.ts`. Route handlers are named `async function`s with typed `request: Request, response: Response`, not inline arrows. Express 5 sends errors thrown in async handlers to the error handler, so there's no try/catch just for that.
- `backend/src/types/`: TypeScript interfaces (not classes: the data always arrives as plain JSON). `blueprint.ts` (`Blueprint`, `Field` and one interface per property type, `ListItemType`), `asset.ts` (`Asset`, `AssetData`, `FieldValue`, `Vector2`/`Vector3`, `AssetExport`, `ValueErrors`), `dialogue.ts` (`Dialogue`, one interface per node type, `DialogueEdge`, `DialogueProblem`, `DialogueExport` and its node types) and `backup.ts` (`Backup`) describe the shapes the frontend's `schema/` and `data/` code makes, so **when a saved or exported shape changes there, update its type in the same change.** `project.ts` (`Project`, plus `ProjectContents`: the `{ blueprints, assets, dialogues }` the contents route takes and answers) and `users.ts` (`User`) are the user's own design (PLAN.md §5.6). `User` holds the password hash, so never send a `User` as-is: answer with `{ id, email, displayName, … }`. The frontend stays JavaScript and doesn't use these types; editor-only shapes (drafts with `uid`s, form values, navigation state) aren't typed.
- **Login** uses `express-session` (set up in `app.ts`): the browser holds a signed, httpOnly `connect.sid` cookie (a week, `sameSite: 'lax'`) and the session stays on the server, as a row in MySQL's `sessions` table, so logins survive a restart. `express-mysql-session` keeps them: `sessionStore` in `app.ts`, built on the app's own pool (`db.pool`, the plain pool inside the promise one) with `createDatabaseTable: false`, since `tables.sql` makes the table. Logging in again or out deletes the old row, and the store deletes expired rows by itself every 15 minutes. That timer keeps Node running, so a script or test that imports `app` must `await sessionStore.close()` before `db.end()`. `package.json`'s `overrides` makes every package use the backend's own `mysql2`: `express-mysql-session` pins an old one with security advisories. `request.session.userId` is the logged-in user; `src/types/session.d.ts` gives it its type. `routes/users.ts` has sign-up (`POST /api/users`), `POST /api/users/login` (starts a fresh session with `regenerate`), `POST /api/users/logout` and `GET /api/users/me` (401 when not logged in). `GET /api/users` and the `/:id` routes are for testing until `/me` versions replace them. Register fixed paths like `/me` before `/:id`. One account per email: the `UNIQUE` index on `users.email` refuses duplicates and `isDuplicateEmail()` turns MySQL's `ER_DUP_ENTRY` into a 409 (sign-up and update). Check body values with `typeof` before using them, since `!value` only checks that something was sent. `validatePassword()` (8+ characters, at most 72 bytes via `bcrypt.truncates`) and `validateDisplayName()` (1–64 characters after trimming) return a message or `null`, like `validateAssetKey()` in the frontend; login only checks the password's type. Error answers are `{ message }`; field-level validation errors will be `{ errors }` (PLAN.md §6).
- `backend/src/projectAccess.ts`: everything in GameAtlas belongs to a project, so the asset, blueprint and dialogue routes all begin the same way. `openProject(request, projectId)` checks there's a session and that the caller is a member, and hands back `{ project, status, message }` — a null `project` means answer with that status and message (401 not logged in, 400 no `projectId`, **404** not a member, so nobody can discover which project IDs exist). `withTransaction(work)` runs writes that belong together, such as a row and the project's ID list (PLAN.md §5.6 rule 2). `addToProjectList` / `removeFromProjectList` change those JSON arrays, and `isDuplicateKey(error)` turns MySQL's `ER_DUP_ENTRY` into a 409. **Row locking (`SELECT … FOR UPDATE`, §5.6 rule 1) isn't built yet.**
- **Route files have three `// region` sections, in this order** (see `routes/users.ts`, which is the model for the rest): *Express Routing* defines the router and attaches each endpoint function to it; *Endpoints* holds one named `async function` per HTTP method, each with a doc comment naming its method and path; *Helpers* holds the column lists, finders, validators and anything else reused between endpoints or lifted out to keep an endpoint readable.
- **How a request names its project:** `projectId` is a query parameter on GET and DELETE, and a body field on POST and PUT. `{id}` in a URL is the row's UUID for assets, dialogues and projects, but the snake_case ID for blueprints (which is only unique inside a project, so those routes always need `projectId` too). A blueprint `PUT` whose body `id` differs from the URL's renames it, and `renameLinksToBlueprint` moves the links in other blueprints and dialogues in the same transaction. An asset `PUT` whose body `key` differs from the saved one renames the asset the same way: `renameLinksToAsset` (in `routes/assets.ts`) rewrites links to it in every other asset with the shared `replaceReferences()` and speakers and given items in every dialogue with `renameAssetInDialogue()`, writing only rows that change and leaving their `updatedAt` (and an asset's `schemaVersion`) alone. The asset's links to itself follow too, and its validation counts it under the new ID.
- **Moving a store to the API** (assets, blueprints and dialogues, all done 2026-10-16) followed one template, which any new store should follow too: (1) `frontend/src/api/<things>.js` wraps list/create/update/delete; (2) the store keeps the current project's list in memory, `load…(projectId)` fetches it, and save/delete call the API, wait, put the server's answer into the list, and answer `{ data }` or `{ error }` (never change the list before the server agrees); (3) the hook keeps returning the plain list and adds a `use<Thing>(…)` lookup with a `status` for loading / found / missing / failed; (4) editors `await` save and delete, disable their buttons while waiting, and show `result.error` in an error toast; pages about one record render `<LoadingRecord>` until it's found. List pages stay as they are.
- **Replacing a whole project:** `PUT /api/projects/:id/contents` (body `{ blueprints, assets, dialogues }`, in their saved shapes) is the one route that writes many rows at once, for the Settings page's restore, reset and delete all, and for filling a new project. It runs `checkContents()` on the set (against itself, never the database), answers 400 `{ message }` on the first problem, and otherwise deletes the old rows, inserts the new ones with fresh UUIDs and rebuilds the project's ID lists in one transaction. It keeps blueprint versions, asset `schemaVersion`s and asset and dialogue timestamps (a missing timestamp becomes now; blueprints have none). To answer with what it saved, it uses the finders the GET routes use, which their route files export: `findBlueprints` and `cleanBlueprint` (`blueprints.ts`), `findAssets` (`assets.ts`), `findDialogues` and `asText` (`dialogues.ts`).
- `backend/sql/tables.sql`: the `CREATE TABLE` statements for all six tables (`sessions` is `express-mysql-session`'s own layout, so keep its column names), to run once against the `gameatlas` database. There is no migration tool.
- `backend/src/db.ts`: the shared `mysql2/promise` pool. Write plain SQL with `?` placeholders (never build SQL by joining strings); JSON columns come back as objects.
- **TypeScript as Node runs it** (type stripping): import local files with their `.ts` extension (`'./db.ts'`), use `import type` for type-only imports, and no enums, namespaces or constructor parameter properties. `tsconfig.json` enforces this, and `allowJs` lets the backend import the frontend's `.js` modules with relative paths (`'../../frontend/src/schema/validation.js'`).
